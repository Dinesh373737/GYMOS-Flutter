4. What to retain, remove, and replace from the existing GymOS
4.1 Retain conceptually
• Multi-tenant society/gym concept with Admin and Resident/member roles.
• Authentication and member management.
• Exercise library with muscles, equipment requirements, difficulty, instructions, and movement type.
• Gym equipment inventory and availability state.
• Maintenance issue reporting and admin resolution workflow.
• Workout planning and workout logging with sets, reps, weight, duration, and RPE-like session effort where appropriate.
• Exercise alternatives when required equipment is unavailable.
• Progress/history analytics.
• Muscle training-load/readiness visualization, but rename and reframe the old “fatigue percentage” so it is clearly an estimate rather than medical truth.
4.2 Remove completely
• The separate DAA algorithm visualizer application.
• Any UI whose purpose is to show BFS, DFS, Knapsack DP tables, heaps, Greedy selection, or Topological Sort for coursework demonstration.
• User-facing “algorithms used” labels.
• Features that exist only because the old assignment required a named algorithm.
• Hardcoded/demo-only flows presented as real production behavior.
4.3 Replace or simplify
• Replace the fixed Greedy recommendation score with a maintainable constraint + personalization engine based on actual user history, available equipment, time budget, goal, preferences, recent training load, and form-check history.
• Replace forced Knapsack workout selection with straightforward domain logic that produces sensible sessions. A deterministic optimizer is acceptable if it helps, but it must not exist merely to demonstrate DAA.
• Replace BFS/DFS branding with an “exercise alternatives” service using explicit relationships plus similarity/eligibility scoring.
• Replace the old exact “muscle recovery percentage” with “estimated training readiness” or “recent training load” and make the uncertainty clear.

10. Workout personalization engine
Do not delegate workout generation entirely to the LLM. Build deterministic constraints first, then allow the agent to orchestrate and explain the result.
10.1 Hard constraints
• Only select active exercises the user can reasonably perform with currently available required equipment.
• Respect the requested time budget and session focus.
• Respect user experience level.
• Avoid immediately re-targeting a muscle group with very high recent training load unless the user deliberately overrides it.
• Do not include an exercise marked incompatible/unavailable because of equipment status.
• Keep exercise order sensible: warm-up/preparation before demanding compounds; accessories later; cooldown/flexibility optional.
• Keep plan size realistic for the selected duration.
10.2 Soft personalization
• Historical exercise frequency and recent volume.
• User preferences and exercises repeatedly skipped/replaced.
• Form-check history: if an exercise repeatedly receives weak technique cues, prefer a simpler variation or include a technique note rather than silently increasing difficulty.
• Variety without random churn: avoid repeating the exact session too often while preserving useful progression.
• Available equipment in the user’s society gym.
• Goal and preferred session duration.
Return a structured `WorkoutPlan` plus human-readable rationales. Rationales must be short and based on actual app data, e.g., “Barbell bench is under maintenance, so dumbbell press was selected.”
11. Workout session mode (must-have)
Build a polished “Today / Workout” flow where the user can execute the generated plan. This is not live rep counting; the user manually confirms/logs sets.
• Show one exercise at a time with set targets, previous-session reference, rest timer, instructions, and alternative button.
• Allow manual logging of reps/weight/duration/RPE-like effort.
• Allow quick add/remove set.
• Allow exercise replacement if equipment becomes unavailable.
• Persist each completed set to the backend, not only at the end of the workout.
• On completion, show a concise summary: duration, sets, exercises, volume where applicable, and readiness/training-load update.
• Never implement camera-based automatic rep counting in the MVP.
12. Photo-based AI/CV Form Coach (centerpiece)
The MVP must analyze a still photo, not live rep counting. This keeps scope achievable while still demonstrating computer vision.
MVP behavior
User selects an exercise and a checkpoint/pose, the app guides camera positioning, ML Kit detects 33 pose landmarks on-device, Flutter computes exercise-specific joint/line metrics, the app shows technique cues plus analysis confidence, and only derived metrics are sent to Serverpod for history unless the user explicitly chooses to retain the image.
Start with four static checkpoints only:
• Squat - bottom-position check.
• Push-up - bottom-position/body-line check.
• Plank - body-line/alignment check.
• Overhead press - lockout/alignment checkpoint OR biceps curl elbow-angle checkpoint; choose whichever is more reliable during implementation.
For each supported checkpoint, define deterministic metrics using detected landmarks. Examples include knee angle, hip angle, torso inclination, shoulder-hip-ankle line deviation, left/right symmetry, elbow angle, and landmark confidence. Use thresholds as technique cues, not medical diagnoses.
UI states must include:
• No person detected.
• Important landmarks out of frame.
• Low confidence / retake photo.
• Analysis complete.
• Checks passed / checks needing attention.
• History comparison.
Do not output an unsafe binary promise such as “your form is safe” or “you will not get injured.” Use language such as “technique cue,” “alignment check,” and “confidence.”
13. Training readiness / load
Retain the useful concept from the existing GymOS heatmap but remove false precision. Build a derived readiness system from recent workouts, exercise muscle contribution, set volume, effort, and time since last training.
Recommended display bands: READY / MODERATE LOAD / HIGH RECENT LOAD. Optionally show a 0-100 internal score, but the primary user-facing UI should be a band plus explanation rather than pretending to measure biological recovery exactly.
Example explanation: “Chest has high recent training load because you trained pressing movements yesterday. Today’s plan prioritizes back and legs.”

16. Agentic GymOS Coach
The coach must not be a generic chat box that forwards text to an LLM. Implement it as a Serverpod-hosted tool-using agent with bounded function calls and structured application context.
Use Groq local function/tool calling on the server, with `openai/gpt-oss-120b` as the default agent model. The Flutter client sends the user message to `AgentEndpoint`; the Serverpod backend provides the allowed tool declarations; Groq returns structured tool-call requests; Serverpod executes those tools; tool results are returned to Groq; and Groq generates the final user-facing response. Keep the model ID configurable so a faster/lower-cost Groq model can be substituted without UI changes. Never expose the Groq API key to Flutter.

Agent rules:
• Maximum bounded tool-call loop (e.g., 6-8 calls per user turn). Prevent infinite self-calling.
• Read tools may run automatically. Any destructive write must require explicit user intent. Creating a draft is non-destructive; deleting history or changing admin data is not.
• Log every tool execution to `AgentAction` with safe summaries, status, and duration.
• Never invent workout history, equipment state, event availability, or form results. If data is absent, say so.
• Keep health/fitness responses general and non-diagnostic. If a user reports pain or an injury, do not diagnose; recommend stopping the painful movement and seeking qualified guidance.
• Do not expose internal chain-of-thought. Explain recommendations using concise data-backed reasons.
• If Groq is unavailable, the core app must still work. The agent should show a clear temporary-unavailable state rather than blocking workouts.
Example high-value agent flow:
User: “What should I train today? I have 40 minutes.”Agent → get_recent_workouts      → get_training_readiness      → get_available_equipment      → create_workout_draft      → final response with short reasons + “Start workout” CTA

30. Coding standards for Astra
• Prefer small, testable services and widgets with descriptive names.
• Keep business logic on the server when it determines shared/persistent behavior; keep camera/pose processing on-device when it protects privacy and reduces latency.
• Use repository/service abstractions where they reduce coupling, but avoid ceremonial architecture with dozens of empty layers.
• Use Serverpod-generated models/client types rather than duplicating DTOs manually.
• Handle null/error states deliberately.
• Add comments only where the reasoning is not obvious; do not narrate every line.
• No dead code, commented-out old implementations, or unused packages in final branch.
• Keep external-provider adapters behind interfaces so AllEvents/Groq can be swapped without touching UI code.
• Use UTC timestamps in storage and convert to local time in presentation.
• Add indexes for common history, society, status, and time-based queries.
• Protect write operations with authentication/authorization checks on the server, not just hidden UI buttons.
